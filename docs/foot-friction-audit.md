# 足部摩擦力能否解决滑步

维护日期：2026-09-24。工具 `scripts/humans/audit_friction_budget.py`，
证据 `artifacts/humans/friction_budget/report.json`。
[全部文档](README.md) · [当前计划](../task_plan.md) · [键盘控制](keyboard-control.md)。

## 结论

**不能。摩擦力是必要的卫生条件，但按本机数据只能解释约五分之一的滑步。**

三条独立证据指向同一结论：

1. **现役摩擦系数已经和真实世界同一量级。** 人体碰撞体**没有任何物理材质**，
   走的是 PhysX 默认 0.5；地板 `wood_floor` 动态摩擦 0.55，PhysX 默认按平均合成
   → 有效 μ≈0.525。真实鞋-木地板约 0.5-0.7。系数不缺，「像真实世界一样加摩擦」
   没有可加的余量。
2. **真正不真实的是法向载荷，不是系数。** 根部外力把 **82% 体重**举在空中，
   地面只承担 **17%** 体重（两脚合计 120 N，对照体重 706 N）。摩擦上限是 μN，
   于是脚底可用剪切力只有 64 N，真实人在同一地板上是 ~353 N。
   要靠「加系数」补回这 5.5 倍差距需要 μ≈2.9，那已经不是真实世界的摩擦。

   口径：下文所有「地面法向力 / 体重」都是**全身地面反力（两脚合计）**，
   这样才与体重可比。单脚数字在双支撑期会减半，不可直接对照。
   力平衡自检（`cycles`，均为该会话中位数）：外部执行器竖直 **581 N** + 地面 **120 N**
   = 701 N，对体重 706 N，差 0.7%（身体在缓慢竖向加减速）。
   执行器竖直分量的分解：配置重力补偿 0.7×72×9.81 = **494.4 N**，
   加竖直弹簧项 `kp·(target_z − root_z)` 中位数 **89.2 N**，合计 583.6 N ≈ 实测 581.1 N，
   两者相关 0.784。也就是说**弹簧把骨盆托得比腿给出的位置更高**，
   多举了约 89 N，脚上因此更轻——配置写的 0.7 实际上跑成了 0.82。
3. **只有约四分之一的滑动是摩擦受限的。** 其余四分之三滑动的切向需求
   **低于**摩擦上限，也就是说接触点本来就没被摩擦力卡住，是控制和参考把脚带走的。

分母不是摩擦系数，而是「脚上还有多少重量」和「参考本身有没有踩住」。

## 两个必须先说清的量测缺陷

### 缺陷 1：人体根本没有摩擦材质

`/World/Human/*/collider` 只带 `PhysicsCollisionAPI`、`PhysxCollisionAPI`、
`PhysxContactReportAPI`（见任一 `human_trial.usda`），**没有 `MaterialBindingAPI`**。
场景材质库（`src/sim2sense_fall/scenes/materials.py`）只绑到环境几何上。
因此：

- 摩擦系数不在任何配置里，无法声明、无法扫描、试验产物里也不记录；
- `support_loss` 扰动（滑面）在配置里被显式声明为「未实现」，
  理由正是「需要实时改地板碰撞体或摩擦，本机未验证」
  （`configs/humans/human_smpl_multiaxis.yaml`）。

现在没有任何地方可以「把脚的摩擦调大」——这是要先补的。

### 缺陷 2：摩擦力从来没有被记录过

`HumanRuntime.contact_samples` 存的是 PhysX 接触报告里的 `record.impulse`。
在全部分档会话上检查：**3286 个非零冲量样本，每一个都与自己的接触法向平行，
最大偏差 2.22e-16**（地板和墙面接触都算）。也就是说该字段是**法向冲量**，
切向（摩擦）分量恒为零。

后果：`floor_contact_slips_m_s` 量的确实是接触点滑速（口径本身没错），
但**摩擦力本身在这个管线里从未被测量**。任何关于摩擦力的判断都只能从动力学反推。

## 方量测：摩擦需求

对整体用牛顿定律，`W` 为重力、`F_a` 为记录的根部外力、`F_c` 为地面接触力：

```
m * a_COM = W + F_a + F_c      =>      F_c = m * (a_COM + g) - F_a
```

地面水平，所以 `F_c` 的水平分量全部是摩擦：

```
mu_required = |F_c_horizontal| / |F_c_vertical|
```

`a_COM` 由记录的关节角走 CPU 正向运动学求质心后两次差分（`rig.forward_kinematics`，
本项目的独立实现，不是复述 USD）。

**正向对照（方法自检）**：重建的法向载荷 vs 接触日志实测的法向冲量，
`cycles` 为 **p50 120 N vs 122 N**（差 2 N），`locomotion_v4` 为 **122 N vs 122 N**。
重建能复现实测量，横向数字才可信。

`cycles`（2040 帧，10413 个踝-地板接触样本）：

| 量 | 值 |
| --- | ---: |
| 地面承担体重比（p50） | 0.17 |
| 根部外力竖直分量（p50） | 581 N = **0.82 体重**（配置只写 0.7） |
| `mu_required` p50 / p95 / p99 / max | 0.198 / 0.674 / 1.401 / 2.679 |
| 超过假定 μ=0.525 的帧比例 | 11.5% |
| 超过 μ=1.0 的帧比例 | 2.0% |
| 滑动帧（> 0.15 m/s） | 355 / 1933 = **18.4%** |
| 其中切向需求 ≥ 摩擦上限 | **86 帧 = 24.2%** |
| 摩擦受限的滑动 slip p50 | 0.358 m/s |
| 其余四分之三的滑动 slip p50 | **0.528 m/s（更大）** |

最后两行是关键：如果滑步的主因是摩擦不够，摩擦受限的那批应该更严重；
实测恰好相反，**需求低于上限的那批滑得更快**。

### 有效系数被数据自己认出来了

滑动帧的 `mu_required` 直方图在 **[0.5, 0.6) 出现最高单峰（69/355）**，
正对应「PhysX 默认 0.5 与地板 0.55 平均」推出来的 0.525。滑动时接触在饱和，
所以这个峰就是真实生效的系数。它同时证明两件事：

- 假定值 0.525 是可信的，不是随手写的；
- 摩擦确实在饱和——只是只在少数帧饱和。

同区间里 144 个帧有 69 个在滑（48%），而整体加载帧只有 18.4% 在滑，差 2.6 倍。
摩擦信号是真实的，量级是次要的。

### 稳健性

`a_COM` 要两次差分，结论对平滑窗有依赖。滑动中「摩擦受限」的比例：

| 平滑窗（帧 / ms） | 3 / 25 | 5 / 42（默认） | 9 / 75 | 15 / 125 | 25 / 208 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 摩擦受限滑动占比 | 20.4% | **24.2%** | 31.4% | 39.1% | 44.2% |

默认 5 帧，最坏情况下也不到一半。**「摩擦只能解释少数滑步」在全部取值下成立。**

### 跨会话

| 会话 | 地面承担体重 | 滑动帧占比 | 摩擦受限滑动占比 |
| --- | ---: | ---: | ---: |
| `cycles` | 0.17 | 18.4% | 24.2% |
| `locomotion_v4` | 0.17 | 19.9% | 18.5% |
| `locomotion_v6` | 0.00 | 25.8% | 52.5% |
| `locomotion_v8` | 0.00 | 37.1% | 62.7% |
| `actions_final`（**无根部辅助**） | **1.00** | **1.1%** | 0.0% |

`actions_final` 是反向对照：那一档辅助是关的，地面承担全部体重，
`mu_required` p50 = **0.004**，几乎没有滑动。注意它只做站立/蹲起，
不是行走，所以它不是「同类动作开关辅助」的干净对照——但它说明
**地面一旦真的承重，切向需求就小到摩擦根本用不上**。

`v6`/`v8` 的「摩擦受限占比」反而更高，是因为那里地面几乎不承重
（实测法向 p50 = 2 N），比值分母趋零、数值不稳。这两档的高比例不能当证据。
力平衡同样自洽：执行器竖直 p50 **703 N = 1.00 体重**，地面 2 N，相加 705 N ≈ 体重——
这两档基本是**被悬着走**，脚只擦地。

## 为什么加摩擦也留不住脚

1. **法向载荷被辅助拿走了。** 摩擦上限 μN 与 N 成正比。辅助举走 82% 体重，
   上限就掉到 17%。把 μ 从 0.525 提到 1.0 只把 64 N 变成 120 N，
   仍是真实世界 353 N 的三分之一。
2. **切向需求不是物理量，是控制器给的。** 需求由 57 个 PD 关节目标
   加一个上限 1500 N 的根部弹簧共同决定。摩擦把脚冻住，需求不会消失，
   它会转成关节跟踪误差，或者由根部弹簧继续拖——弹簧上限 1500 N，
   而脚底摩擦上限只有 64-120 N，弹簧每次都赢。
3. **参考本身没踩住。** `task_plan.md` P0-B 已归档：现役两条 AMASS 片段里
   被标「支撑」的脚自身中位滑 0.134/0.108 m/s，世界冻结锚点按构造不可达，
   残差 111 mm，97.5% 的步都顶在 IK 预算上。**摩擦留不住一个目标在动的脚。**

## 定位为「未验证的假设」

脚部碰撞代理是长 0.228 m 的**胶囊**，不是平面脚掌。胶囊与地面是一段线接触，
绕自身长轴滚动时库仑摩擦不提供任何阻力矩（滚动阻力是另一回事，量级极小）。
这可能是一部分「脚在原地转」的来源。本文件的滑速口径量的是接触点切向速度，
纯滚动时该量为 0，所以**滚动不会被现有指标捕获**。这一点本轮没有量测，
不得据此下结论。

## 下一步（待定，未执行）

要真正回答「加多少摩擦有用」，必须在**同一动作**下扫 μ 并同时量测
法向与切向冲量。前置条件与设计：

1. **补人体材质**（当前完全缺失）：在 `rig` 段声明人体/足部摩擦，
   给碰撞体 author `UsdPhysics.MaterialAPI` + `MaterialBindingAPI`，
   足部单独一份，并写进试验 provenance。这同时解掉 `support_loss` 的阻塞。
2. **补摩擦量测**：低层接触报告的 `impulse` 只有法向分量，
   但 `isaacsim.sensors.experimental.physics.ContactSensor.get_raw_data()`
   给出的 `ContactRawData.impulseX/Y/Z` 是**世界坐标三分量**
   （Isaac Sim 6.0 文档：`isaacsim::sensors::experimental::physics::ContactRawData`）。
   用它才能直接读出 μ = |J_t| / J_n，不必再靠动力学反推。
3. **扫 μ**：至少 {0.05, 0.525, 1.0, 2.0}，同一片段同一 seed。
   **正向对照必须有**：μ→0.05（冰面）必须让滑速显著恶化，
   否则说明这条通道根本没接上，不能把「μ 调大没变化」当成结论。
4. **判据**：滑速 p95 与 `floor_contact_slip` 超限比例。
   预期（本文件外推）：μ=1.0 消除约四分之一滑动帧，其余仍在。

在跑这个之前，按本文件第 1、2 节，代价更低的两个方向是：
让地面真的承重（降 `gravity_compensation_fraction` 或改成只补竖直分量），
以及回到 P0-B 的「参考有没有踩住」——那才是剩下的四分之三。

## 2026-09-24 路线 2 实跑：让地面真的承重（A/B 已执行）

上节三条结论给出一个可检验的预测：如果滑步受摩擦限制，那么把法向载荷还给地面就该
减少滑动。**已实施并实跑，预测被否证——摩擦指标全面变好，实际滑动反而更多。**

### 改动

`root_wrench` 原来只在竖直方向加 `gravity_compensation_fraction · m · g`，位置弹簧随后还能
**再往上推**，所以执行器实际举得比配置多。新增 `max_vertical_lift_fraction_of_weight`：
对执行器的**总向上力**设硬上限，使配置写的比例成为真正的天花板。

- `src/sim2sense_fall/humans/root_control.py`：新字段 + `__post_init__` 校验
  （不得超过 1；**不得低于 `gravity_compensation_fraction`**，否则夹的是补偿本身而不是
  反馈项——报错信息直接教你去降补偿比例）+ `root_wrench` 里的夹取。
- `configs/humans/root_assist.yaml`：**出厂值 1.0**（见下，0.7 是实测回退，不采用）。
- 回归 3 条 + 变异检查：删掉夹取那一行，2 条测试立刻失败。

### A/B（同配置、同 seed、同 10.3 s demo，各一条确定性运行）

`artifacts/humans/assist_cap_ab/{before,after}/`，`before` 用 cap=1.0 复现改动前行为
（该臂关节误差 5.703°、滑速 p95 0.6573，对上历史基线 5.719° / 0.651）。

| 指标 | cap 1.0（改动前） | cap 0.70 |
| --- | ---: | ---: |
| 地面法向（p50） | 122 N（0.17 体重） | **212 N（0.30 体重）** |
| 执行器竖直（p50） | 586 N = 0.83 体重 | **494 N = 0.70 体重** |
| `mu_required` p50 / p95 | 0.206 / 0.832 | **0.163 / 0.642** |
| 需求超过 μ 的帧 | 14.2% | **8.6%** |
| 滑动帧占比 | 22.0% | **38.1%（更差）** |
| 其中摩擦受限占比 | 36.1% | **13.6%** |
| 报告滑速 p95 | 0.6573 m/s | **0.6739（更差）** |
| 超 0.15 m/s 的样本 | 14.0% | **30.7%（更差）** |
| 最大关节误差 | 5.703° | **8.713°（更差）** |
| 皮肤最低 Z | +2.98 mm | +2.97 mm |

**读数**：载荷侧它完全按设计工作——地面正好变成预测的 212 N，执行器被压回配置的 0.70，
摩擦受限的滑动从 36.1% 降到 13.6%，需求超过上限的帧从 14.2% 降到 8.6%。
**但总滑动从 22.0% 涨到 38.1%，滑速与关节跟踪同时变差。** 原因是腿扛不动多出来的载荷：
骨盆下沉、PD 误差从 5.703° 涨到 8.713°，**下沉本身变成脚的运动**。

这同时印证并强化了本文件的核心结论：**系数和载荷都不是那个瓶颈。** 把脚变得更能抓，
它并没有抓得更牢——它滑得更多了。剩下的四分之三滑动是控制/参考问题。

**决策**：`root_assist.yaml` 出厂值取 **1.0**（同一旋钮最松的一端），0.7 按实测回退不采用。
旋钮保留，因为后续工作需要它，而且它让「未加夹取时的上浮」变成可声明、可量测的量。
每条臂只有一次确定性 demo，不是统计；要改这个值请自带一次实跑。

**口径保留**：cap=1.0 在 max 处确实夹到了 706.3 N（旧行为无夹取），所以该臂比真正的旧行为
略多一点载荷、略少一点摩擦受限滑动——即这次对比对 `after` 的劣势略有**低估**。

### CPU 反事实（上节）与实际对比

反事实预测 cap=0.70 时 249 个滑动里只剩 23 个摩擦受限（−54%）。实测摩擦受限从 90 降到 62
（−31%），但**总滑动涨了 83%**，所以净效果是负的。反事实只移动 μ 的分母、冻结运动，
它高估了收益——这正是它被标成「上界」的原因。

## 2026-09-24 路线 3 起步：参考踩不住的来源（一个假设已被否证）

P0-B 已归档「参考自身被标支撑的脚中位滑 0.134/0.108 m/s」。本轮先做归因，**否证了一个
我自己的假设**，并留下一个未否证的线索。

**被否证的假设：把根速度从「常数」换成「源片段自己的根平移」就能让脚踩住。**
现役实现把 `gait.speed_m_s` 设为**两脚合并后的中位支撑退行速度**，而控制器以常数速度推进根。
若这个替换是漂移主因，那么改用源根平移应当明显改善。实测（1300 帧/腿，用项目自己的
travel-support 掩码）：

| 根运动来源 | 左踝世界速度 p50 | 右踝世界速度 p50 |
| --- | ---: | ---: |
| 源片段自己的根平移 | 0.115 m/s | 0.098 m/s |
| 常数中位速度 | 0.114 m/s | 0.148 m/s |

**几乎没变。** 所以漂移在根输运**上游**，不是根速度替换造成的。
（⚠️ 这一条随后被 [支撑掩码审计](support-mask-audit.md) C 节**收窄**：它只在
**掩码中位帧**上成立。在「最慢脚」这个更该用的量上，源根把「帧内存在一只 <0.05 m/s 的脚」
从 26.9% 抬到 40.7%（前进）、21.4% 抬到 34.5%（后退）——源根确实救回了约三分之一的近静止帧。
原来的表述过宽，现按实测收窄。）

**仍成立的线索（口径已更正）**：两条腿的支撑退行速度不同。前进片段（`CMU/08/08_04`）
左 0.721 / 右 0.966 m/s，而 `gait.speed_m_s` 是两者合并的中位 0.777；后退片段
（`CMU/08/08_11`）两腿几乎一致（1.091 / 1.080），**所以不对称是前进片段特有的**——
而它正是 09-24 为修右臂新换的源。

⚠️ 本节初稿写的「差 34%」是**比较口径错误**（那是在世界坐标上量的）。在骨盆相对量
（`gait.speed_m_s` 就是它的中位数）、且只取两腿都被标的相位窗上复算，前进片段为
**左 0.736 / 右 0.960，差 23.4%**。更正与完整实测见
[支撑掩码审计](support-mask-audit.md) D 节。该审计**没有**做源片段重定向前自身的左右对照，
所以**仍然不能**把不对称归因到源或重定向，只记录为线索。

⚠️ 本节的归因结论按该审计**收窄**：上面「源根 vs 常数根」用的是**掩码中位帧**。
在「最慢脚」这个更该用的量上源根明显更好（<0.05 m/s 的帧 **40.7% vs 26.9%**，前进）。
所以「常数根速不是主因」只在掩码中位帧上成立；掩码中位帧本身不是一个可信的集合
（见该审计 A、B 节）。
