## app.update() 时序缺陷（已实测、已修复）

- `probe_loop_timing.py` 实测：本 build 上一次 `app.update()` 推进**固定 1/60 s 物理
  时间**（dt=1/120 时每 update 2 步），与 `omni.kit.loop-isaac` 开关无关（两模式
  byte-identical），注入 GUI kit 的 `runLoops.main.manualModeEnabled/rateLimitEnabled`
  也无效。自由落体正对照：60 updates = 1.0 s，球落 4.946 m ≈ ½g·1.0²。→ 所有按
  「秒→update 数」换算的窗口都跑了 2 倍物理时间。
- `SimulationManager.step(steps=n, update_fabric=False)` 是确定性步进器：恰好 n 步，
  自由落体吻合（1.247 m vs 1.226 m@0.5 s）。`update_fabric=True` 与
  `timeline.set_play_speed(0.5)` 一样会静默原生崩溃（exit 0 无 traceback）。
- 修复（Fix B）：`common.py::step_physics(steps)` —— manager.step + 步数读回断言
  （静默失败变成显式 RuntimeError）；verify.py `hold()`/rest-sample、simulate.py
  settle/逐帧循环全部换用。`GRAVITY_SETTLE_SECONDS` 3.0→6.0（旧标定是在 2× 时序下
  完成的，物理时长实为 6 s，保真换算）。
- 复验：**verify_multiaxis_stepper.log 全绿 37 PASS / 0 FAIL**（重力：下降 1.1031 m、
  末段 200 ms 蠕动 0.085 mm；PD 跟踪 11.5°<15°；穿地 -0.0000 m）。
